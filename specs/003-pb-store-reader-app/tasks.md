# Tasks: PB Store on the Reader

**Input**: Design documents from `/specs/003-pb-store-reader-app/`

**Prerequisites**: plan.md, spec.md (with the clarifications of 2026-10-28), research.md, data-model.md, contracts/ (`store-state-folder.md`, `launcher.md`, `engine-additions.md`, `device-interfaces.md`, `store-rules.md`, `ui-pages.md`), quickstart.md, and the checklists `install-safety.md`, `ux.md`, `security.md`, `requirements.md`

**Tests**: REQUIRED. Constitution Principle I (Test-First, non-negotiable) applies. In every phase the test tasks come first, are written before the code they cover, and MUST be run and **seen failing** (a compile error for a missing header counts as failing) before the implementation tasks start; each test group ends with a task that builds and runs the tests one at a time and records why each fails. No task is done while a test fails. Every `tests/**/test_*.cpp` is its own executable: build and run one at a time (`cmake --build build --target test_store_service_list`, then `ctest --test-dir build -R test_store_service_list`) so a red test does not hide the others. Shell tests (`tests/launcher`, `tests/packaging`) and the scripted walks (`tests/walks/*.walk`, run by `scripts/ui-walk.sh`) are tests in the same sense: written first, seen failing.

**Organization**: Tasks are grouped by user story. Build order differs from the numbering of the spec, for two reasons given by the owner: **Browse (US1) comes first and is demonstrable on the host before any write path exists**, and **Recover (US6) comes second, before Install (US2)**, and no write path of the store is used on a real reader until Recover is done. Then Install (US2), Update (US3), Remove (US4), Adopt (US5), Update itself (US7), About/Settings/Log (US8). The device checks are split: **phase 5** (before any write path of the store; the first task is a read-only copy of `applications/` and `system/config/desktop/`) and **phase 12** (the store's own write paths). The last phase holds the version, the documents, the complete About screen and the release.

**Labels**: `[US1]`…`[US8]` are the spec's user stories. **MANUAL** tasks need the owner or a real device and are skipped by an automated implementation run; they never invent URLs, keys, hashes or secrets. `{T}` references inside a task name another task by its id.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- All paths are relative to the repository root `/home/voneinem/Projekte/appstore-pocketbook`
- Rule ids: installer rules `E-INS-01…38`, `W-INS-01…04` ([docs/installer-rules.md](../../docs/installer-rules.md)); store rules `E-STO-01…10`, `W-STO-01…03` ([contracts/store-rules.md](contracts/store-rules.md)); catalog and package rules `E-CAT/E-PKG/E-ENT` as in `docs/contracts/`
- "Byte-identical" means: same relative paths, kinds, sizes and SHA-256; timestamps and permissions are ignored; implemented once in `tests/support/tree_compare.h`
- Reference code that already exists (reuse, do not copy): `core/include/pbstore/*`, `core/install/include/pbstore/install/*`, `tests/support/{install_rig,tls_test_server,package_fixtures,sample_catalog,sample_app,fake_reader,crash_fs,fat_rules_fs,tree_compare,keys,run_tool,tmp_dir,test_support}.h`; sibling projects for patterns only: `~/Projekte/nextcloud-pocketbook`, `~/Projekte/notes-pocketbook` (no secret, fixture or data folder is ever copied from them)
- The SDK location comes only from `$POCKETBOOK_SDK` or `-DSDK_PATH`; no path is written into any file

## Implementation Strategy

### MVP first (Browse + Recover, then Install)

1. Phases 1 and 2: gates, engine additions, the policy modules, the launcher start path, a package.
2. Phase 3 (Browse): **stop and demonstrate on the host** with `scripts/run-host-demo.sh` and the walk `01-browse.walk`.
3. Phase 4 (Recover): stop; it is the gate for every write path.
4. Phase 5 (device checks A): the owner copies the reader aside and runs the read-only and own-folder checks. Fix what they find (each fix test-first).
5. Phase 6 (Install): the first real MVP — browse, install, survive a cut at every step.
6. Then Update, Remove, Adopt, Self-update, About/Settings/Log; device checks B; polish and release.

- Every device fact that is not Observed is labelled Unverified in the documents and has a MANUAL task here (constitution 2.1.0); the design works either way, so the host phases do not wait for the device.
- Commit after each task or logical group; the version gate and the constitution gate run in `scripts/pre-merge.sh`.
- Never mark a checklist item of `checklists/*.md` as done from this task list: those boxes belong to the reviewer.
